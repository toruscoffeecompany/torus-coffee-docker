Torus Coffee Company - Supabase Schema Draft
Last updated: 2026-05-29

Purpose
This is the first draft of the Supabase/Postgres data model for the Torus Coffee Company website. It is a planning document, not final SQL yet.

Design Goals
- Keep product data clean and reusable.
- Support public shop pages.
- Support manual inventory first.
- Support admin editing later.
- Support blogs and content.
- Support optional customer accounts later.
- Support product feeds and future Square integration.
- Protect sensitive/private data with RLS.

Important Security Assumption
Supabase Row Level Security must be enabled for all tables that contain anything beyond public read-only content.

------------------------------------------------------------
1. profiles
------------------------------------------------------------
Purpose:
Store customer/admin profile info connected to Supabase Auth users.

Fields:
- id uuid primary key, references auth.users.id
- email text
- first_name text
- last_name text
- phone text
- role text default 'customer'
- marketing_consent boolean default false
- marketing_consent_at timestamptz nullable
- created_at timestamptz
- updated_at timestamptz

Roles:
- customer
- editor
- inventory_manager
- admin

RLS idea:
- Users can read/update their own profile.
- Admin can read/manage all profiles.

------------------------------------------------------------
2. categories
------------------------------------------------------------
Purpose:
Product categories for shop filters and feeds.

Fields:
- id uuid primary key
- name text not null
- slug text unique not null
- description text
- sort_order integer default 0
- active boolean default true
- created_at timestamptz
- updated_at timestamptz

Initial categories:
- Freeze-Dried Candy
- Freeze-Dried Fruit
- Seasonal
- Gift Boxes, later
- Variety Packs, later

RLS idea:
- Public can read active categories.
- Admin can manage categories.

3. products
------------------------------------------------------------
Purpose:
Main product records.

Fields:
- id uuid primary key
- sku text unique not null

- slug text unique not null
- status text default 'draft'
- category_id uuid references categories.id
- short_description text
- full_description text
- flavor_notes text

- net_weight_oz numeric
- price_cents integer not null
- sale_price_cents integer nullable

- taxable boolean default true
- quantity_on_hand integer default 0
- low_stock_threshold integer default 5
- track_inventory boolean default true
- square_payment_link_url text
- square_item_id text nullable later
- square_variation_id text nullable later
- shipping_weight_oz numeric
- ships_us_only boolean default true
- requires_shipping boolean default true
- ingredients text
- allergens text
- storage_instructions text
- shelf_life text
- main_image_url text
- image_alt_text text
- social_share_image_url text
- seo_title text
- seo_description text
- google_product_category text
- brand text default 'Torus Coffee Company'
- condition text default 'new'
- gtin text nullable
- mpn text nullable
- featured boolean default false
- badge text nullable
- sort_order integer default 0
- admin_notes text nullable, admin-only
- created_at timestamptz
- updated_at timestamptz

Product statuses:
- draft
- active
- hidden
- sold_out
- archived

RLS idea:
- Public can read products where status = 'active' or status = 'sold_out', but only public-safe fields should be queried/exposed.
- Admin can manage all products.

Note:
Because RLS does not easily hide columns by role if public queries select them, app queries/API views should avoid returning admin-only fields publicly. Consider a public_products view later.

Storage Buckets
------------------------------------------------------------

Recommended buckets:
- product-images
- blog-images
- brand-assets
- private-exports, later and protected if used

Bucket rules:
- Public read for published images.
- Admin-only upload/update/delete.
- Originals should also remain locally backed up.

------------------------------------------------------------
Initial Migration Approach
------------------------------------------------------------

1. Create categories.
2. Create products table.
3. Seed launch products from catalog CSV.
4. Add image paths when selected.
5. Add Square links when created.
6. Add RLS policies before production use.
7. Add blog/contact/email tables when those features are implemented.

------------------------------------------------------------
Open Schema Decisions
------------------------------------------------------------

1. Store product gallery images in product_images table or JSON array on products?
Recommendation: product_images table.

2. Use rich text JSON or Markdown/text for blog body?
Recommendation: body text/Markdown initially.

3. Store admin-only fields in products table or separate private table?
Recommendation: products table is acceptable if public queries are controlled carefully; public view can be added later.

4. Should contact submissions be stored, emailed, or both?
Recommendation: both, after anti-spam/rate limiting exists.

5. Should exact inventory counts be exposed through public product query?
Recommendation: no. Public query should return display status only.
